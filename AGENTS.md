# Project Architecture Rules

- Google review automation belongs to Campaign Studio; database completion triggers reserve a person-wide request and a single self-removing timer claims one channel under a shared locked daily budget. Guest check-in is not completion; use the separate staff completion action. Confirm reviewers manually using contact/account identity, never Google names or link clicks. Why: prevent premature, duplicate or sentiment-filtered requests and avoid idle polling costs.

- A frozen or past-due membership never blocks portal routing; benefits and facility access are enforced separately by status-aware UI and authoritative database functions.
- Paying a future membership-freeze fee records payment only; the date-driven freeze activation path changes membership status on the scheduled Detroit date. Exception: the daily freeze-billing sweep pre-pauses dues (void) for an approved, paid freeze when the next renewal falls before the start and would bill frozen time (`_shared/freezePrePause.ts`). Why: a renewal the day before a freeze charged a member a full frozen month.
- Freeze endings share freezeResume: server intent, Stripe marker/key, verified full-period anchor (no proration), atomic completion and retryable errors; repair skips ended/restarting freezes. Why: no duplicate charges, re-pauses or unbilled time.
- Package-backed PT is payment_status 'pass' by trigger. Booking holds a session; an hourly job completes past uncancelled sessions, consuming the hold or an available package once (otherwise unpaid), without notifications. Returns are admin-only. Why: no double deductions or false unpaid states.
- PT attendance uses checked_in_at, scheduled/completed status and Detroit days; report PT separately. Why: member identity must not hide PT arrivals.
- Therapist blocks feed spa busy slots and conflict checks; date-locked triggers guard booking and block writes. Why: training must remain unbookable.
- A cancelled membership never counts as membership for pricing or portal access: member-rate checks and `useUserMembership` ignore `status = 'cancelled'`, so those people use the non-member portal and prices while their history stays. Why: cancelled members must not buy at member rates.
- Campaign lists paginate and de-dupe lowercase emails. Why: selects cap at 1,000.
- Scheduled campaign emails use self-removing one-time timers, never polling. Why: no idle costs.
- Targeted texts use admin_person_activity() as the single per-person activity source; campaigns snapshot recipient user IDs plus phone-only imported contacts, and every send goes through send-sms without bypassConsent. send-sms accepts consent from the account, or by phone from non-member signup or imported contacts (phone_sms_consent), but an account opt-out always wins; STOP/START updates every source. Why: one source for segments, and carrier consent rules are never skipped.
- Revenue and sales-tax reports read only `revenue_ledger` (built by `sync-revenue-ledger` from Stripe balance transactions plus cash/check/Clover sales); never sum app tables like `manual_charges` or `cafe_orders` for revenue. Refunds are negative lines in the month issued, and tax, card fees and tips are kept separate from revenue. Why: per-report table sums double-counted register sales, missed dues, PT and cash, and changed closed months.
- Billing may only change a member's status between 'active' and 'past_due', always through `apply_billing_status_change`; frozen, cancelled, expired and pending-activation members are never changed by billing. Why: a frozen member's paused Stripe subscription still reports 'active', and activations stay a staff decision.
- Scheduled jobs authenticate to edge functions only with the vault-held internal task token: job commands call `public.internal_task_token()` and functions check it through `_shared/internalTaskToken.ts`. Never write a token, key or secret into a migration, job definition or source file. Payment-confirmation functions (`isServerCaller`) accept only the service-role key. Why: a plain-text token committed to the public repo let anyone call internal functions.
- Spa intakes are per appointment and typed by service: wrap services use `spa_body_wrap_intakes` (drawn signatures, practitioner sign-off only by staff via trigger), other massage/body services use `spa_intake_forms`; pick the type with `intakeKindFor()`. Why: each service needs its own consent, and both feed the profile Forms list.
- Staff intake viewers share the complete service-specific summary and print only that summary in an isolated document. Why: therapist copies must include every recorded answer and signature without payment controls.

- Read subdirectory `AGENTS.md` before editing there.
- Commitment displays use membershipCommitment's start date plus merged actual freeze days, separate from membership_end_date. Why: historical freezes extend terms once without cancelling memberships.
- Kids Care renewal fulfillment reads legacy and current Stripe line pricing and creates one payment-deduplicated pass per paid invoice cycle, never resets the parent's latest pass. Why: current invoice formats skipped renewals and multi-child subscriptions could overwrite each other's sessions.
- Spa availability launch dates live on availability windows and are enforced by shared calendar helpers and an appointment trigger. Why: future launches must allow reservations now without permitting appointments before their start date.
- Abandoned applications share an email-deduplicated roster for filters/export and paginate history; resolved/test rows never get reminder controls. Why: counts must match the full list without making members leads.
- Spa request alerts and request handling views reuse `useSpaServiceRequests` across admin and front desk, with front desk links staying within its shell. Why: both staff entry points must show the same pending requests without sending staff into a different portal.
- Admin-booked spa appointments for clients without an account store guest_email; a profiles trigger links them to the account created with that email, and the confirmation email carries a create-account-and-sign-waiver link. Why: public requests need no account, but booked clients must end up with an account and waiver.
- Spa badges/checkout require a payment intent for card/account money; explicit desk tenders count. Voucher/credit checkout retains payment_method and stores covered base value plus actual extra tender in covered_checkout, ignoring legacy credit amount_paid. Why: never charge covered services again or confuse prices with collected money.
- Only one pending membership application per email is allowed (database unique index); the apply form treats that rejection as a successful submit. Why: double taps saved duplicate applications.
- Spa reminder timing uses real UTC instants converted once to Detroit wall-clock fields through send-spa-reminders/timing.ts; stored appointment fields are never reinterpreted as server-local instants. Why: double timezone conversion sent two-hour reminders after the visit.
- Spa duration upgrades resolve the same-treatment menu variant through spaUpgradePricing and a database trigger; checkout itemizes only the menu-price difference, preserving prior payments and original voucher/credit coverage. Unpriced duration-only updates are rejected. Why: longer appointments must not retain shorter-treatment pricing.
- Public seaweed ritual listings group active duration variants for presentation only; booking receives the unchanged selected menu record and shared ritual copy feeds the menu and service page. Why: preserve duration-specific availability, pricing, intake and historical appointment links without duplicating public listings.
- Other body wraps group active shorter/extended variants by their base treatment name; shared research-grounded details feed the public menu and service pages, while booking receives the selected original record. Why: keep durations and live prices accurate without changing the approved seaweed ritual.
- Every class, PT or spa cancellation email from the club is paired with a send-sms text (consent-checked); membership/application cancellations stay email-only. Why: clients must hear about club cancellations by text too.
- Successful staff PT bookings invoke send-pt-booking-email for each saved appointment; it sends consent-checked SMS with appointment-level deduplication independently of email, and notification failures never retry the booking. Why: clients need immediate confirmations without duplicate sessions or texts.
- Class-pass returns use one auth-aware confirmation consumer per page, refresh credits after fulfillment, preserve the saved class until its week loads, and reconcile invalid payment selections; every BookingModal hook runs before null-session returns. Why: checkout returns and opening a class must not crash, lose intent, or use unavailable credits.
- Guest spa checkout: new card, date-locked reserve, one capture; window fit uses treatment length only. Refusals logged/shown verbatim; a self-removing timer closes expired unbooked holds with a stop reason, never succeeded ones. Why: generic refusals and "Incomplete" piles.
- Guest spa date validation permits same-day red-light/dry-cryo recovery services with at least 20 minutes of Detroit-time notice; other treatments remain future-day only. Why: guest checkout must honor the wellness times offered without accepting past slots.
- Guest spa checkout accepts any public anon key; account tokens need verified auth. Why: rotated keys must not break guests.
- Class schedule navigation, calendar selection and displayed days share the horizon from classScheduleWindowEnd. Why: extending visibility must work equally on public and embedded portal schedules without exposing dates beyond that horizon.
- Class schedule conflict checks exclude cancelled occurrence dates, not whole recurring rules or hidden live classes; cancellation refreshes generated-session queries. Why: a cancelled occurrence must not cause a false warning while future real overlaps remain visible.
- Online spa bookings apply Mother's Day vouchers and gift cards in `spa-guest-checkout`: charge only the uncovered part (fully covered = SetupIntent only); lock and redeem the code in `reserve_spa_guest_checkout` with the appointment, release on payment failure. Why: codes must never be reused or charged on top of.
- PT payment-plan sales may override the template's month count per sale (2–24) via installment_count_override on the sale intent; the schedule builder (pt_build_plan_schedule_v3) recalculates the split and templates stay unchanged. Why: staff need flexible plan lengths without creating new templates.
- Book club admin lives on one Higher Self Society page with a Members tab plus one tab per round from SOCIETY_ROUNDS (votes, RSVPs, messages); calendar entries for meetings link to that tab. Why: each event type is managed in one place without extra admin pages.
- Book club self-signups use the member-validated society RPC; legacy next-round inserts require authenticated membership and matching account identity through RLS. Why: public interest forms must not bypass member-only eligibility or guest approval.
- New marketing emails/texts are built and sent from Campaign Studio (`marketing_campaigns` + `campaign-studio` function, brand-locked renderer in `_shared/campaignRender.ts`); do not add new one-off blast senders or per-event send panels. Why: separate panels made sends impossible to find and every email needed new code.
- Massage menu groups 60/90 variants by base name via src/lib/massages.ts; booking receives the selected original record and copy lives in that file. Why: one listing per treatment without changing pricing, intake or history.
- Payroll uses only recorded work via `admin_payroll_sources` + `src/lib/payroll.ts`; shift edits only through `admin_adjust_shift_clock` with a reason; tips separate from gross. Why: auditable pay, no silent hour edits.
- Workout journal: in-progress state in localStorage + `workout_sessions_in_progress` (newest wins); plans in `workout_plan_entries`, Detroit weeks via `workoutJournal.ts`. Why: resume mid-workout.
- 3D exercise demos live in `src/lib/exerciseMotions.ts`, keyed by exact exercise name; never fuzzy-match or reuse a demo for a different exercise. Why: members must never see the wrong movement.
