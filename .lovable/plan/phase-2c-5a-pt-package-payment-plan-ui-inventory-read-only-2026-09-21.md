## 2. Create / edit package — exact field order

Format (select, req) · Display order (number, 10) · Name (text, req) · Sessions (number, 1) · Price $ (number, 0) · Expires in days (number, 30) · Notes (textarea) · Public (switch, on) · Active (switch, on) · Payment plan (switch, off) · Monthly installments (number, 2–24, default 3, shown only when the switch is on).
All map 1:1 to `pt_packs` columns and all are FUNCTIONAL. Saving calls `sync-pt-pack-plan-price`, which creates/updates the Stripe recurring price stored in `payment_plan_stripe_price_id`.

## 3. Sell Package entry point

`/admin/pt/packages` → "Sell package" (also on Clients/Passes screens) opens `SellPTDialog` — a modal.
Steps today: search customer → pick format → pick pack → quantity → activation date → expiration (auto-filled from `expiration_days`, editable) → choose payment (card on file / paid offline / charged externally) → optional "Split into N monthly payments" checkbox → internal notes → totals box → Charge.

## 4. Package selection during the sale

Shown: pack name, price in the dropdown, sessions per pack, price per session, default expiration days.
Not shown: session duration, existing client package balance, any list of plan options.
Staff can change quantity, activation, expiration, and internal notes. Staff **cannot** override price, apply a discount, select a trainer, or pick between plan options — only the single toggle.

## 5. Payment options during the sale

Pay in full FUNCTIONAL · Payment plan PARTIAL (single fixed split) · Predefined plan list MISSING · Custom plan MISSING · Down payment MISSING · Number of future payments MISSING (read from the package) · Frequency MISSING · Installment amount MISSING (derived) · Saved payment method selection FUNCTIONAL (lists cards, default preselected) · Add/update card from this dialog MISSING · Review before sale PARTIAL (totals only, no schedule).

## 6. Autopay date behavior today

- Staff **cannot** choose the first autopay date. No control exists.
- Staff **cannot** choose the billing day of the month.
- The subscription is created with no `billing_cycle_anchor` and `payment_behavior: error_if_incomplete`, so **the first installment charges immediately** and every future payment falls on that same day-of-month, forever anchored to the sale date.
- Future dates are generated by Stripe, not by Storm. Storm stores only `payment_plan_next_payment_date` (one date) on `pt_passes`.
- Staff cannot see the full date list before completing the sale, and cannot edit individual installment dates afterward.
- 29th/30th/31st: handled by Stripe's own clamping (short months bill on the last day). Storm has no rule of its own.
- Timezone: Storm renders stored dates at `T12:00:00` local to avoid day-shift; no America/Detroit-specific logic in the plan path.
- Stored: Stripe holds the authoritative schedule; Storm holds only the next date, installment amount, count paid, total count, total cents, status, and subscription id. The `stripe-webhook` increments paid count and rolls the next date on each paid invoice.

## 7. Payment schedule preview before finalizing

Shown: total package price, amount charged today (per-installment figure), number of payments, per-payment amount, saved card, package expiration.
Missing: total future balance as its own line, exact date of every future payment, explicit frequency label, and any dated schedule table.

## 8. Backend vs UI mismatches

1. Backend creates a real Stripe subscription — Sell UI cannot choose the first autopay date or billing day.
2. Backend accepts `saleRef`, quantity, activation and expiration — UI cannot pass a down payment or custom installment amount.
3. `pt_link_payment_plan` stores installment count, amount, total and next date — Sell UI never previews a dated schedule.
4. `pt_passes` has `price_override_cents` and `sessions_override` — no Sell UI control writes them.
5. `pt_packs` supports exactly one plan shape — no table exists for multiple named plan options.
6. Webhook maintains installments paid / next date / past-due — client-facing portal surfaces none of it.
7. `admin-create-pt-payment-plan` requires a saved card — the Sell dialog cannot collect one, so staff must leave and come back.
8. `pt-retry-installment` exists for failed installments — reachable only from the Billing failed tab, not from the client record.

## 9. Staff client PT billing view

Route `/admin/pt/clients/:userId` — `PTClientBillingSnapshot` + `PTClientFinancialCenter`; deeper detail lives at `/admin/pt/billing` (tabs: Unpaid sessions, Invoices, Autopay & payment plans, Failed & past due, Payment activity, Refunds) with a `PlanDetailModal` timeline.

FUNCTIONAL: active package, sessions total/used/remaining, package price, amount paid, amount remaining, plan status, next autopay, installments paid vs total, previous payments, failed/past-due, payment history, invoices, refunds, Stripe subscription id.
PARTIAL: full upcoming autopay schedule (the timeline in `PlanDetailModal` is *reconstructed by adding calendar months to the single stored next date* — it is an estimate, not Stripe's real schedule) · receipts (Stripe emails them; no link in Storm).
MISSING on the client page itself: the dated schedule (only on the Billing page modal), the payment method on file, and a retry-installment action.

## 10. Client-facing view

`/portal/passes` → `MyPTPassesSection`: sessions remaining, expiration, upcoming sessions, cancel.
MISSING for members and non-members alike: dedicated PT dashboard, package price, autopay status, next payment, full schedule, payment history, failed payments, receipts, invoices, refunds, payment-method management.

## 11. Gap map

**A. Exists and works** — package CRUD with archive-on-sold, Stripe price sync, single equal-split plan, saved-card selection, idempotent sale path, webhook installment tracking, staff billing workspace with invoices/refunds/failed payments.

**B. Backend exists, staff UI does not expose it** — price and session overrides, dated schedule data, retry-installment from the client record, plan detail on the client page, receipts.

**C. Needs to be built** — multiple named plan options per package, down payment separate from installments, staff-chosen first autopay date and billing day, dated schedule preview before the sale, add-a-card inside the Sell dialog, Storm-side installment schedule rows, client-facing PT billing view.

## What it takes to reach the target flow

1. New `pt_pack_payment_plans` table (plan name, down payment, installment count, frequency, per-installment amount or derive) + editor UI on the package form.
2. New `pt_payment_plan_installments` table so Storm owns every dated installment instead of one next-payment field; webhook marks them paid.
3. Sell dialog: plan-option picker, first-autopay-date control (with 29–31 clamping rule, America/Detroit), and a dated schedule preview table before confirming.
4. `admin-create-pt-payment-plan`: accept `firstPaymentDate` and a down payment — charge the down payment as a one-off, set `billing_cycle_anchor`/`trial_end` so installment one lands on the chosen date, and write the installment rows.
5. Add-card-in-dialog via a Stripe setup intent so a sale never stalls on a missing card.
6. Client billing panel on `/admin/pt/clients/:userId`: real schedule, payment method, retry action, receipts.
7. Member/non-member PT billing view reading the same installment rows.
