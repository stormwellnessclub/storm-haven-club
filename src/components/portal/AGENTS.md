- Every client screen (PT page, dashboard cards, bookings history) reads PT data only through `pt_my_portal()`/`pt_my_requests()`; clients have no direct read or write policies on PT appointments, passes, payments, installments, refunds, usage or requests, and cancel only via `cancel_pt_appointment`. Why: those rows carry staff-only notes columns.
- Client PT requests: options/times come only from `pt_client_request_options()`/`pt_client_request_times_all()` (every eligible trainer together, one-hour blocks from each trainer's window start; `pt_client_request_times()` is the single-trainer variant) (start times only, via the internal `pt_client_slot_is_open` + `pt_check_slot_core`, which add class conflicts), requests are created only by `pt_request_create` and read via `pt_my_requests()` (no client policies on training_requests); the portal keeps the approved Overview → Request Session → Requests + Upcoming layout and requests never create appointments. Why: request rows hold staff notes and clients must never see trainer calendars.
